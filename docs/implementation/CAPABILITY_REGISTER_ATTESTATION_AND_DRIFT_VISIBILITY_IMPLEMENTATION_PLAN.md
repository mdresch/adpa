## PR1 — Attestation deadline and drift-reason visibility on the Capability Register (ADR-013 Action Items 1–3)

**Depends on**: nothing in-flight. Extends only already-shipped ADR-012 read paths (`CapabilityRegistryRepository.listForUser`, `Capabilities.razor`) and already-shipped ADR-005 data (`capability_registry.attestation_due_at`, `capability_activation_history.reason`) — no migration, no new endpoint, no new job.

**Objective**: close two related read-path gaps in the Capability Register. First, the one ADR-012's own Consequences section named but didn't scope — `Capabilities.razor` already renders `pending_re_approval` as its own status chip, but a reviewer has no way to tell, from the Register itself, whether that's config/control drift or a lapsed attestation, and no visibility into an approaching `attestation_due_at` before the hourly sweep (`capabilityAttestationJob.ts`) acts on it. Second, a portfolio-identification gap surfaced once the PR7 discovery view shipped: every card identifies its portfolio by raw UUID (truncated in `Capabilities.razor`, shown in full in `app/capability-registry/page.tsx`), even though `portfolio_governance.portfolio_name` already exists and is one join away.

**Tasks**:
1. Extend `CapabilityRegistryRepository.listForUser` (`server/src/modules/capabilityRegistry/CapabilityRegistryRepository.ts`) to additionally select `attestation_due_at`; join `portfolio_governance` for `portfolio_name`; and — via a `LEFT JOIN LATERAL` scoped to `activation_status = 'pending_re_approval'` — the `reason` of that capability's most recent `capability_activation_history` row **whose own `new_status = 'pending_re_approval'`**:
   ```sql
   SELECT cr.id, cr.module_id, cr.portfolio_id, pg.portfolio_name, cr.platform_operator, cr.functional_owner_type,
          cr.functional_owner_department, cr.control_definition_owner_department, cr.activation_status,
          cr.attestation_due_at, pra.reason AS pending_re_approval_reason
   FROM capability_registry cr
   JOIN portfolio_governance pg ON pg.id = cr.portfolio_id
   LEFT JOIN LATERAL (
     SELECT reason FROM capability_activation_history h
     WHERE h.capability_id = cr.id AND h.new_status = 'pending_re_approval'
     ORDER BY h.changed_at DESC LIMIT 1
   ) pra ON cr.activation_status = 'pending_re_approval'
   WHERE ${scopeClause}
   ORDER BY cr.module_id, cr.portfolio_id
   ```
   The `portfolio_governance` join is a plain `JOIN`, not `LEFT JOIN` — `capability_registry.portfolio_id` is `NOT NULL REFERENCES portfolio_governance(id)`, so it always resolves and can never itself produce a missing row (`server/migrations/433_capability_registry.sql:9`). Filtering the history subquery on `new_status = 'pending_re_approval'`, rather than simply `ORDER BY changed_at DESC LIMIT 1` against all of a capability's history, is the corrected form from ADR-013's own review: `promote_capability_status` writes `activation_status` and its history row atomically, so today the two forms agree for any capability actually in `pending_re_approval` — but the filtered form directly answers "why did this become pending re-approval" rather than depending on that invariant continuing to hold as the transition graph evolves. The `LATERAL` join's `ON` condition means that subquery only executes for rows already in `pending_re_approval`, so its added cost scales with how many capabilities are in that state, not the size of the register. Map the new columns onto the repository's return type as `attestationDueAt`, `portfolioName`, and `pendingReApprovalReason` (`null` only for the last one, when the LATERAL join produces no row).
2. `CapabilityRegistryController.listForUser` already passes the repository's row shape straight through via `res.json({ capabilities })` — confirm the three new fields serialize as camelCase (`attestationDueAt`, `portfolioName`, `pendingReApprovalReason`), matching every other field in this response; no other controller change. Confirmed separately that the orchestrator's own relay (`RelayList` in `orchestrator/Adpa.Orchestrator/Controllers/CapabilityController.cs`) forwards the raw response body as a string rather than deserializing into a typed C# model, so this Node-side change needs no corresponding orchestrator change — only the Blazor page's own DTO (Task 3) reads the new fields.
3. Extend `Capabilities.razor`'s `CapabilityRegistryEntry` DTO (`orchestrator/Adpa.Web/Components/Pages/Capabilities.razor`) with `AttestationDueAt` (`DateTimeOffset?`), `PortfolioName` (`string`), and `PendingReApprovalReason` (`string?`). Replace the card's current `Shorten(item.PortfolioId)` display with `item.PortfolioName`. Render, directly under each card's existing `StatusChip`: the reason as a small subline (same `font-size:12px; color:var(--gp-soft);` weight already used for this page's other helper text) when `PendingReApprovalReason` is set; an attestation badge when `AttestationDueAt` is set — neutral "Attestation due `<date>`" beyond a 14-day warning threshold, warning-styled "Attestation due in `<n>` days" inside it, warning-styled "Attestation overdue" once past due, and no badge at all when `AttestationDueAt` is null. The 14-day threshold is a named `@code`-block constant (`AttestationWarningDays`), not inline, so retuning it later is a one-line change.
4. Extend `CapabilityRegistryListItem` (`lib/api.ts`) with `portfolioName: string`, and update `app/capability-registry/page.tsx` to render `capability.portfolioName` in place of the current `Portfolio {capability.portfolioId}` (the raw, untruncated UUID). This is the only task touching the Next.js tier — the attestation badge and pending-re-approval reason stay Governor-Portal-only per ADR-013's original scope; the portfolio name is a plain identifier already shown (badly) on both surfaces, so it's fixed on both.
5. Update `.agents/skills/adpa-federated-capability-ownership/SKILL.md` per its existing "ADR-0xx addition (date, shipped)" convention (see the ADR-012 PR1 entry already there) plus Key Files rows for the repository's extended query, `Capabilities.razor`'s and `app/capability-registry/page.tsx`'s new rendering, and the new Contract Guard test file.
6. Contract guard: a capability seeded into `pending_re_approval` via a simulated drift demotion returns a `pendingReApprovalReason` containing "drift detected on"; one seeded via a simulated lapsed-attestation demotion returns that path's reason; a capability with a synthetic later `capability_activation_history` row whose `new_status` is not `pending_re_approval` (seeded directly for the test, since `promote_capability_status` cannot itself produce this today — its transition graph only allows `pending_re_approval -> active|disabled`) still returns the correct demotion reason, proving the query filters on `new_status` rather than trusting recency alone; a capability not currently in `pending_re_approval` returns `pendingReApprovalReason: null` regardless of its history; `attestationDueAt` round-trips a set value and is `null` when the column is unset, independent of `activation_status`; every returned row's `portfolioName` matches its `portfolio_id`'s seeded `portfolio_governance.portfolio_name`. Real-Postgres integration test (a mocked pool can't meaningfully exercise the `LATERAL` join's own logic), landed under `server/src/__tests__/modules/federated-capability-ownership/capabilityRegistryAttestationVisibility.test.ts` — already covered by the packet's existing `testPathPattern`, no manifest edit required. Neither UI piece is Jest-covered (`orchestrator/` has no Jest harness; the Next.js page change is a one-line rendering swap); verify both manually against the same seeded scenarios, consistent with how ADR-012's own Blazor pieces were verified.
