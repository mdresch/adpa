# ADR 009: Unified Authentication Across Tiers (Firebase as the Single Identity Provider)

## 1. Status
**Accepted (2026-07-13)** — decision items 3-5 (`Adpa.Web`'s server-side Firebase sign-in, session-as-cookie, token refresh, bearer relay, and `[Authorize]` on pages) are implemented; see [the implementation design spec](../superpowers/specs/2026-07-13-adr009-governor-portal-auth-design.md). Item 2 (closing the legacy-JWT hardcoded-fallback-secret risk on the Node side) and the Open Questions remain unaddressed.

Deciders: Owner(s) of the Express backend, the Next.js frontend, the .NET Orchestrator, and the Governor Portal (`Adpa.Web`).

## 2. Context

ADPA has three tiers that each need to know who a user is, and today they know it three different ways — none of which was ever decided in an ADR. This document exists because ADR-005 Phase 6 hit the gap directly: the first human-triggerable write endpoint to `capability_registry` (`POST /api/v1/capability-registry/:moduleId/:portfolioId/promote`) could be built and authenticated on the Node side, but its Blazor UI half had to be deferred outright — `orchestrator/Adpa.Web` has no way to know who is clicking the button.

**What each tier actually does today, verified against running code:**

- **Node/Express (`server/`)** — `authenticateToken` (`server/src/middleware/auth.ts:39-220`) is a *dual-path* verifier: it sniffs the JWT header for a `kid` claim (`isFirebaseIdToken()`, line 26) to decide whether to call `admin.auth().verifyIdToken()` (Firebase path, line 74) or fall back to `jwt.verify(token, process.env.JWT_SECRET || "your-secret-key")` (legacy path, line 93). The legacy path's hardcoded fallback secret is a live risk, not a hypothetical — nothing prevents it from being reached in an environment where `JWT_SECRET` was simply never set. Either path resolves to a DB row (`SELECT id, email, role, permissions, is_active FROM users ...`, lines 122-127); `role`/`permissions` are Postgres-authoritative, not JWT claims. Firebase users with no existing row are JIT-provisioned with default permissions (lines 140-189). `POST /api/v1/auth/{register,login,demo}` (`server/src/modules/auth/AuthController.ts`) issue legacy `jwt.sign()` tokens directly — this is the intended dev-mode path documented in CLAUDE.md, gated by `NODE_ENV !== "production"` for `demo` (line 371) unless `ALLOW_DEMO_IN_PROD` is set. A `POST /auth/bootstrap-elevation` route (line 442) also exists for cold-start admin self-elevation and is currently undocumented anywhere in this repo's architecture docs.
- **Next.js frontend (`app/`, `contexts/AuthContext.tsx`)** — Firebase-client-SDK-driven. `onAuthStateChanged` fetches a Firebase ID token, hands it to `apiClient.setToken()`, and `lib/api.ts` attaches it as `Authorization: Bearer <token>` on every proxied `/api/*` call (`lib/api.ts:913,1055`). `demoLogin()` bypasses Firebase and hits Node's `/auth/demo` directly.
- **.NET Orchestrator (`Adpa.Orchestrator`)** — `Program.cs:42-57` *does* configure real JWT Bearer authentication (`Authority = https://securetoken.google.com/{FIREBASE_PROJECT_ID}`, issuer/audience validated against the same Firebase project Node and Next.js use — one shared Firebase project, confirmed via `.env.example`'s single `FIREBASE_PROJECT_ID`/`NEXT_PUBLIC_FIREBASE_*` pair). `UseAuthentication()`/`UseAuthorization()` run in the pipeline, but `AddAuthorization()` is never called and `[Authorize]` is used nowhere in this codebase — a deliberate choice (documented inline in `CapabilityController.cs` and reaffirmed by `TaskApprovalGate`'s own comments) because `Governance:ApprovalsEnforced=false`'s dev-bypass needs to run *before* any attribute-based gate would fire. `TaskApprovalGate.cs:105` and `DepartmentClaimsReader.cs` do read the validated JWT's `departments` claim manually — so the pipeline already trusts and parses Firebase-issued tokens, it just never requires one at the transport layer.
- **`Adpa.Web` (Blazor Governor Portal)** — confirmed zero authentication. No `AuthenticationStateProvider`, no `CascadingAuthenticationState` in `App.razor`, no login page. The single named `HttpClient("api")` (`Adpa.Web/Program.cs:23-27`), used by `Ledger.razor`, `Requirements.razor`, `RPASGovernanceCenter.razor`, and `AIWorkspace.razor`, never attaches an `Authorization` header — so any authenticated endpoint it calls (including ADR-005 Phase 6's new `promote` proxy) 401s today.

**Prior art in this repo, and why it's stale rather than authoritative:** `docs/07-architecture/AUTH_DECISION_DEFERRED.md` (2025-10-26) and `AUTHENTICATION_STRATEGY_ANALYSIS.md` both evaluate **Supabase Auth** vs. custom JWT and defer a decision; `ENTERPRISE_AUTH_ENTRA_ID_STRATEGY.md` proposes Entra ID fronted by Supabase Auth. All three predate the codebase's actual, undocumented migration to Firebase Auth (client SDK + Admin SDK + orchestrator JWT Bearer against `securetoken.google.com`) — none of them reflect what's running today, and none of them anticipated a fourth tier (`Adpa.Web`) needing its own answer. This ADR supersedes all three for authentication strategy; they remain useful as historical record of the Supabase-era evaluation, not as current guidance.

**Why this is one ADR and not three tier-specific patches:** the risk this document is written against is the same one ADR-005 opens with — a system that looks governed tier-by-tier while no single place actually defines who a user is. Node, Next.js, and the orchestrator already agree (by accident of incremental migration, not decision) that Firebase is the identity source; codifying that agreement, and closing the one tier that never got the memo, is cheaper and less risky than inventing a fourth model for `Adpa.Web` alone.

## 3. Decision

Adopt **Firebase Authentication as the single identity provider across all four tiers**, formalizing what Node/Next.js/orchestrator already do in practice, and extend it to `Adpa.Web` rather than inventing a separate scheme for the Governor Portal.

1. **Firebase is canonical identity; Postgres `users` remains canonical authorization.** No tier re-implements sign-in against a different provider. `role`/`permissions`/`departments` continue to live in Postgres and Firebase custom claims (already synced via `server/src/modules/departments/firebaseClaimsAdmin.ts`) — this ADR does not change that split, only formalizes that Firebase is the only accepted token issuer going forward.
2. **Close the legacy-JWT fallback risk.** `server/src/middleware/auth.ts`'s non-Firebase path (`jwt.verify(..., process.env.JWT_SECRET || "your-secret-key")`) must fail startup in production if `JWT_SECRET` is unset, matching the fail-closed treatment `firebaseAuth.ts` already applies to missing Firebase credentials in production (`critical: process.env.NODE_ENV !== "development"`). The legacy path itself is retained (dev/demo login still needs it, per CLAUDE.md), only the silent-hardcoded-secret failure mode is closed.
3. **`Adpa.Web` gets server-side Firebase sign-in, not a client-side SDK.** Blazor Server executes on the server, so the existing pattern used by SPA clients (Firebase client SDK issuing tokens to browser JS) doesn't apply and shouldn't be copied. Instead: a login page posts credentials to Firebase's Identity Toolkit REST `signInWithPassword` endpoint server-side, the resulting ID token + refresh token are held in an encrypted, `HttpOnly`, server-side session (ASP.NET Core cookie authentication, `AddCookie`), and the ID token is silently refreshed ahead of its ~1h expiry using Firebase's `securetoken.googleapis.com` refresh endpoint. No Firebase client SDK ships to the browser.
4. **The session's Firebase ID token is attached to the existing `"api"` `HttpClient`**, via a `DelegatingHandler` reading the current `HttpContext`'s session — not a new HttpClient, not a change to `Ledger.razor`/`Requirements.razor`/etc.'s existing injection pattern.
5. **`AddAuthorization()` + `[Authorize]` are adopted for `Adpa.Web`'s own Razor pages/components** — this is a different app from `Adpa.Orchestrator`, so it does not conflict with the orchestrator's deliberate non-use of `[Authorize]` (item 6 explains why that stays unchanged). Governor Portal pages that currently render dead "Approve"/"Review" buttons become the actual authenticated front door ADR-005 Phase 6 Task 7 asked for.
6. **`Adpa.Orchestrator` keeps its current model unchanged.** `AddAuthorization()`/`[Authorize]` are *not* retroactively added to `Adpa.Orchestrator`'s controllers — the existing reasoning (dev-bypass ordering, downstream fail-closed checks in `TaskApprovalGate` and Node's `authenticateToken`) still holds and this ADR doesn't reopen it. What changes is only that `Adpa.Web` will now actually *have* a bearer token to relay, where today it has none.
7. **`bootstrap-elevation` gets documented, not removed.** Its existence should be recorded here rather than left as an undocumented cold-start mechanism discovered by accident; scoping/restricting it further is an open question (§6), not a blocking precondition for the rest of this ADR.

## 4. Options Considered

- **A. Adopt Firebase everywhere, extend to `Adpa.Web` (chosen).** Zero new identity providers; reuses the one Firebase project already shared by three of four tiers; `Adpa.Orchestrator` already validates this token shape. Cost is building a server-side (not SDK-based) sign-in flow for Blazor Server specifically, since no tier has done that yet.
- **B. Token relay / SSO from the Next.js frontend — no independent `Adpa.Web` login at all.** Governor Portal would only be reachable by a user who already authenticated in the Next.js app, forwarding that session's token. Rejected as the primary mechanism: the Governor Portal is meant to be usable by department approvers who may have no reason to ever use the Researcher Dashboard, and coupling one tier's availability to another's session is a worse failure mode than it saves in implementation cost. May still be worth offering as a convenience *in addition to* a real login (open question, §6).
- **C. Revisit Supabase Auth or Entra ID (the pre-Firebase proposals).** Rejected: would mean migrating Node and Next.js *off* their already-working Firebase integration to solve a gap that only exists in the one tier (`Adpa.Web`) that has no auth yet — solving a zero-tier problem by re-solving three already-solved tiers.
- **D. Bespoke ASP.NET Core Identity for `Adpa.Web` only, independent of Firebase.** Rejected: recreates the exact "three different answers to the same question" problem this ADR exists to close, just makes it four.

## 5. Consequences

- **Positive:** One identity provider, one set of custom claims (`departments`, synced via the existing `firebaseClaimsAdmin.ts`), reasoned about once instead of per-tier. Unblocks ADR-005 Phase 6's deferred UI half and any future `Adpa.Web` work that needs to know who's asking. Closes a live, unforced security gap (the hardcoded JWT fallback secret) as a side effect rather than a separate effort.
- **Negative:** `Adpa.Web` takes on session-management complexity (encrypted cookie storage, refresh-token rotation) that no other tier in this codebase has had to implement server-side before — this is new surface area, not a copy of an existing pattern.
- **Risks:** A Blazor Server session cookie is a different attack surface than a stateless bearer token (session fixation, cookie theyft if `HttpOnly`/`Secure`/`SameSite` aren't all correctly set) — mitigated by using ASP.NET Core's own cookie authentication middleware rather than a hand-rolled session store, but this must be reviewed as carefully as any other credential-handling code before it ships.

## 6. Open Questions

1. Should `Adpa.Web` offer option B (relay a Next.js session) as a convenience alongside its own login, for users who are already signed into the Researcher Dashboard? Not required for this ADR's core decision.
2. Should `POST /auth/bootstrap-elevation` be scoped further (e.g. one-time-use, IP-restricted, disabled outside initial deploy) now that it's documented here for the first time? Tracked as follow-up, not blocking.
3. Who owns rotating/monitoring the shared Firebase project's service-account credentials across three consuming tiers (Node Admin SDK, orchestrator JWT Bearer validation, and the new `Adpa.Web` REST sign-in call)? Currently implicit; should get an explicit owner once this ADR is accepted, consistent with ADR-005's own ownership argument.
