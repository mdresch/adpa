# ADR 005: Federated Capability Ownership for Module Activation

## 1. Status
**Proposed (2026-07-09)**

Deciders: Owner(s) of the Orchestrator governance ritual pipeline, the Governor Portal, and platform architecture.

## 2. Context
The motivating argument (from the author's article on role-based system literacy, drafted alongside this ADR) is: when a system executes work rather than just recording it, centralizing its operation in IT while leaving accountability for its outcomes with the business department (HR, Finance, Legal, Risk & Compliance) creates a structural gap. The failure mode isn't a broken system — it's a *correctly configured* system that nobody accountable for its output actually owns. Microsoft Purview rollouts (per BlueVoyant's implementation guidance and Microsoft Learn's permissions documentation), expense-management adoption stalling at 39–47% (Softjourn's 2026 trends report), and HR stacks fragmenting across 16+ disconnected applications (Whatfix's HCM adoption research) are cited as three independent mechanisms producing the same outcome. The proposed fix, borrowing federated governance and three-lines-of-defense from data-governance and risk-management literature, is to split platform operation (IT), functional/control ownership (the accountable department), and operational execution (shared) into distinct, enforced roles — rather than trusting the split to hold as an unenforced norm.

ADPA is exposed to exactly this risk today, and the exposure is verified in code, not hypothetical:

- **No capability has a declared owner.** There is no `functionalOwner`/`controlDefinitionOwner`/department field anywhere in `orchestrator/`, `server/`, or `governance/` for a module, template family, or governed-feature packet. `governance/RPAS.md:251` asserts "every artifact... has a verifiable owner" in prose, but nothing in schema enforces it.
- **The one real approval gate is role-blind.** `TaskApprovalGate`/`TaskApprovalAttestation` (`orchestrator/Adpa.Orchestrator/Services/TaskApprovalGate.cs:16-116`) genuinely blocks `phase0/approve` and `rtm/apply-amendment` without a valid attestation — but `DecidedBy` is a free-text string. It cannot express "only the Compliance owner may approve this," only "someone approved this."
- **No account-level department concept exists to check against.** `department` appears only as free text on per-project/per-record tables (`resource_capacity_settings.department`, `stakeholders.department` — `server/migrations/000_baseline.sql:5853,7230`) — there is no `users.department` or equivalent identity-level field. A department-scoped gate has nothing to authenticate against today.
- **The Governor Portal cannot be used to approve anything.** `Ledger.razor` and `RPASGovernanceCenter.razor` render "Review"/"Approve"/"View Audit" buttons with no `@onclick` handlers. The backend gate exists; a human department reviewer has no UI to exercise it.
- **The governance ledger isn't tamper-evident.** `governance_ledger` (`orchestrator/Adpa.Orchestrator/Migrations/20260416215635_AddGovernanceLedgerAndAuthorityTokens.cs:31-49`) has no hash column. Hash-chaining (`prev_hash`/`hash`, SHA-256 via trigger) already exists, but only on the unrelated `server/` app-level `audit_log` table (`server/migrations/000_baseline.sql:566-567`) — the tier that's supposed to be the governance authority doesn't have the proof mechanism the tier next to it already proved out.
- **What ADPA already has, and shouldn't rebuild:** DRACO (`server/src/services/dracoReviewBoard.ts`, `dracoService.ts`) is a real, running three-agent advisory board (Evidence Validator / Governance Evaluator / Counterfactual Challenger); `template-lifecycle`'s `templates.development_status` state machine (draft → ... → compliance → archived, `server/migrations/000_baseline.sql:11336-11410`) is a mature, stored-procedure-enforced activation lifecycle with a full audit trail. Both are directly reusable.

## 3. Decision
Adopt **federated capability ownership** as an enforced architectural property of ADPA, not a documented convention: every governed module/capability declares three distinct owners, and activation is gated behind the accountable department's sign-off rather than a platform-level toggle.

- **`platformOperator`** — always IT / the Orchestrator. Owns system administration, access control, integrations.
- **`functionalOwner`** — the accountable business department (e.g., Compliance owns `compliance`, Legal or Risk owns `ip-governance`). Owns activation approval and day-to-day policy fit.
- **`controlDefinitionOwner`** — the party that defines the control/policy itself, which may differ from `functionalOwner` (e.g., Legal defines a retention control that Compliance operationally owns).

This is enforced through six concrete mechanisms, each extending something that already exists rather than inventing new plumbing:

1. **Capability ownership registry** — extend `server/governed-features.manifest.json` packets (or a new adjacent table) with `platformOperator`/`functionalOwner`/`controlDefinitionOwner` fields per packet/module. Ownership is not a one-time entry: each assignment carries an attestation deadline (e.g. quarterly), and a lapsed attestation automatically transitions the module to `pending-re-approval` (item 4) rather than leaving a stale owner silently in place — an unmaintained registry is exactly how this mechanism decays back into ceremony, the same risk ADR-001 flagged for the stakeholder role catalog. The registry must also stay in sync with `governed-features.manifest.json` going forward, not just at initial seeding: a new module can otherwise ship with a manifest entry (satisfying CI) but no `capability_registry` row, meaning it never enters this lifecycle at all and runs permanently unrestricted. Extend the existing `verify:governed-features` check to fail when a manifest packet has no corresponding registry row, or vice versa.
2. **Identity extension (prerequisite)** — add a department/accountable-role attribute at the account level. Nothing today plays this role; the closest fields (`resource_capacity_settings.department`, `stakeholders.department`) are per-record free text, not identity.
3. **Department-aware approval gate** — extend `TaskApprovalAttestation` so `DecidedBy` is checked against the requesting department (from #2) and the module's `functionalOwner` (from #1), not accepted as an arbitrary string. The gate also fires when `controlDefinitionOwner` changes the underlying control/policy artifact — a control edit requires `functionalOwner` re-acknowledgment before the module may remain `active`, so "defined in one place, enforced in another" can't recur inside the fix itself. Default behavior on missing, expired, or ambiguous approval is **deny** (module reverts to / stays in `pending-department-approval`); an emergency override requires a second, distinct approver **who is themselves a member of the module's `functionalOwner` department** — not merely any two people, which would recreate the exact bypass this ADR exists to close — plus a logged justification. This exceeds, and does not merely reuse, ADR-004 §4.3's baseline: DRACO's override only requires *a* human justification with no department binding at all, which is not strict enough for a gate whose entire purpose is department-scoped accountability. An override-granted activation is not permanently equivalent to a normal approval: it carries a mandatory expiry (e.g. 72h), after which the module automatically reverts to `pending-re-approval` unless a normal, non-override approval has since been recorded — bounding how long an emergency exception can substitute for the accountable department's actual sign-off. This hardens the override mechanism; it does not fix ordinary approval latency, since the override still requires the same department's involvement (two members instead of one) and does nothing for a department that's slow or unreachable across the board — that remains the SLA/escalation path already flagged in Consequences and Open Question §1.
4. **Module activation lifecycle** — model activation as a state machine (draft → pending-department-approval → active → disabled) copying `template-lifecycle`'s proven stored-procedure + audit-trail pattern, rather than a feature flag. This is a *lifecycle*, not a one-time gate: any change to a module's rules, configuration, or linked control definition transitions an `active` module back to `pending-re-approval` — the gate re-fires on drift, not only on first activation. Module status is writable only through this state machine (mirroring `template_status_history`'s stored-procedure-only writes) — no direct column update — so the ledger in item 6 can be a complete record, not just a tamper-evident one. The same write-path lockdown must cover whatever config/control data actually drives drift detection, not only the status column — if a control's parameters live in a separate table with its own direct-write path, editing them without touching `status` lets a module stay `active` while its behavior silently changes, reopening this exact gap one table over.
5. **DRACO as pre-approval evidence** — surface a DRACO board review to the department approver as the "system literacy" briefing before they decide, reusing the existing board rather than building a new one. The approval attestation must reference the DRACO review's verdict ID as a required field — advisory evidence an approver can click past without engaging is the same failure as the Governor Portal's current decorative buttons, just relocated. A blocking/unfavorable DRACO verdict is itself an override case: `functionalOwner` sign-off alone is not sufficient to activate when DRACO returns REJECT — the same second-approver-from-`functionalOwner`-plus-justification path in item 3 applies, so an unfavorable verdict can be overruled but never silently clicked past. Referencing the verdict ID is necessary but not sufficient engagement: the attestation must record, per individual DRACO finding, whether it was accepted or is being overridden with justification — a single free-text note against an aggregate verdict is still coarse enough to rubber-stamp; per-finding acknowledgment is not. To keep this usable rather than a wall of individual checkboxes that itself gets rubber-stamped, group findings by risk/control category for the primary accept/override decision, with per-finding drill-down available — the requirement is meaningful engagement, not maximum click count.
6. **Tamper-evident ledger** — extend `governance_ledger` with the `prev_hash`/`hash` pattern already proven on `audit_log`, or route activation decisions through `audit_log` directly, so every activation decision is the continuous-accountability record the article calls for. Hash-chaining only proves the entries it contains weren't altered after the fact — it says nothing about whether every consequential action produced an entry in the first place. Coverage, not just integrity, depends on item 4's state-machine-only write path being genuinely exclusive. As a second, independent line of defense — not a replacement for that lockdown — add a periodic reconciliation job comparing live `activation_status` values against the ledger's recorded transitions: an active module with no corresponding activation record, or a config change with no matching drift-triggered entry, is exactly the silent gap a prevention-only design can miss. This makes the ledger a detective control as well as a preventive one. That check alone still only verifies an entry exists, not that the live configuration matches what was actually approved — extend it to compare a content hash of the module's current config/control data against the hash recorded at last approval, so drift that somehow reaches production without tripping the trigger (a bug, a direct restore, a replication edge case) is caught by comparing effective state, not just checking for a matching log row.
7. **A working front door** — wire `Ledger.razor` / `RPASGovernanceCenter.razor` (or a new `ApprovalQueue.razor`) to actually call these endpoints, so a department reviewer never needs to hit the API directly.

**This mechanism is not "live" — and no module may reach `active` status through it — until items 1–3 ship together.** Items 2 and 4–7 can each ship independently and will look like governance (a registry exists, a lifecycle exists, DRACO is wired in, the ledger is hash-chained, the portal has buttons) while the one piece that makes any of it binding — the department-aware check in item 3, which depends on the identity field in item 1 — remains unbuilt. That combination is precisely the Purview failure mode this ADR is written against: a technically complete-looking deployment with no enforced accountability underneath. This must be a structural constraint, not a documentation commitment: the `active` transition's stored procedure requires `functional_owner_department` (populated from items 1–2) as a `NOT NULL` precondition with no default, so completing activation is literally impossible — not merely discouraged — until the identity and ownership fields exist and are populated. A written promise not to ship the gate early is exactly the kind of unenforced norm this ADR argues against; partial delivery must be technically blocked, not just tracked.

## 4. Options Considered

### Option A: Status quo — IT remains sole gatekeeper
| Dimension | Assessment |
|---|---|
| Complexity | None |
| Cost | None upfront, unbounded tail risk |
| Enforces accountability | No |

Cheapest option, and it reproduces the exact failure mode the article documents: modules can go live without the accountable department ever being structurally required to look at them.

### Option B: Policy-only governance (documented expectation, no technical gate)
| Dimension | Assessment |
|---|---|
| Complexity | Low — documentation and process only |
| Cost | Low upfront, relies on discipline holding under deadline pressure |
| Enforces accountability | No — advisory only |

This is what most organizations already have (per the article's Purview/expense-platform examples) and it's precisely what fails: a documented expectation that IT will loop in the business is not a mechanism, it's a hope. Nothing stops a rollout from proceeding without it when nobody is enforcing it.

### Option C (Recommended): Technical enforcement via ownership registry + role-aware gate + lifecycle + hash-chained ledger
| Dimension | Assessment |
|---|---|
| Complexity | High — spans Postgres schema, .NET orchestrator, Blazor UI, and identity |
| Cost | Significant upfront; low recurring once the registry exists |
| Enforces accountability | Yes — structurally, not by convention |

Pros: makes "whose problem is this" answerable before an incident, by construction; reuses three already-real subsystems (DRACO, template-lifecycle's state machine, audit_log's hash chain) instead of inventing parallel ones. Cons: real cross-tier engineering cost; introduces approval latency if a department is slow to respond; the ownership registry itself needs a maintainer or it drifts, same risk ADR-001 flagged for the stakeholder role catalog.

### Trade-off analysis
Option B is the trap, not Option A — it looks like progress (a document exists) while preserving the exact structural gap the article is about: an unenforced expectation collapses under the first deadline that conflicts with it. Option C's cost is real, but it's the only option where a module cannot reach production use without the accountable department's sign-off being a database fact, not a Slack message someone forgot to send.

## 5. Consequences

### Positive
- A department-relevant module cannot go live, or remain live after its rules/control definition change, without that department's approval being a structural precondition, not a courtesy step.
- "Whose problem is this" has a schema answer (`functionalOwner`) before an incident occurs, not during one.
- DRACO gives non-technical approvers the "system literacy" support the article argues roles now require, without turning them into engineers.
- Reuses three subsystems that already work (DRACO, template-lifecycle, audit_log's hash chain) instead of building parallel governance machinery.

### Negative
- Genuine cross-tier build: Postgres schema + orchestrator (.NET) + Governor Portal (Blazor) + identity, likely the largest single governance initiative in the repo to date.
- Approval latency risk — a slow or unavailable department owner becomes a rollout bottleneck; needs an SLA/escalation path, not just a queue.
- The ownership registry requires an owner and review cadence itself, or it decays the same way an unmaintained catalog would (see ADR-001 §5).
- Until the identity extension (item 2) lands, none of the role-aware enforcement (item 3) is possible — this is a hard sequencing dependency, not parallelizable work.

### Explicitly out of scope
Stated plainly so this ADR isn't read as claiming more than it does:
- **Infrastructure-level bypass.** This design defends against application/API-level bypass — a Postgres superuser or someone with direct database access can always disable a trigger, revoke a revocation, or write around any of this. That's an infrastructure access-control problem, not something a schema constraint can solve.
- **Insider collusion.** Two legitimate `functionalOwner`-department members can still jointly approve something they shouldn't. This ADR enforces *who* is accountable for the decision, not the *quality* of that decision — DRACO's advisory board is the only check against pure human misjudgment, and it can itself be overridden by the same two people.
- **DRACO's own robustness.** This ADR treats a DRACO verdict as a trusted input. Whether DRACO itself can be manipulated (prompt injection, model failure) is ADR-004's concern, not this one's.

## 6. Action Items
1. **Extend the identity model** with a department/accountable-role attribute at the account level — prerequisite for everything else; nothing today plays this role.
2. Define the capability ownership registry (extend `governed-features.manifest.json` or add a table) with `platformOperator`/`functionalOwner`/`controlDefinitionOwner` as three independently enforceable fields, not two enforced and one decorative. Each assignment carries an attestation deadline; a lapsed attestation auto-transitions the module to `pending-re-approval` rather than leaving stale ownership in place. Extend `verify:governed-features` to fail on any manifest packet with no corresponding registry row (or vice versa), so a new module can't ship ungated by omission.
3. Extend `TaskApprovalAttestation`/`TaskApprovalGate` to (a) validate `DecidedBy` against the module's `functionalOwner` and the approver's department (depends on 1 and 2), (b) re-fire when `controlDefinitionOwner` edits the linked control, requiring `functionalOwner` re-acknowledgment, (c) default-deny on missing/expired/ambiguous approval, and (d) support an emergency override only via a second distinct approver **who is themselves a member of `functionalOwner`** plus a logged justification — this is stricter than ADR-004 §4.3's baseline (any human, no department check), not a reuse of it as-is. An override-granted activation expires automatically (e.g. 72h) and reverts to `pending-re-approval` absent a subsequent normal approval — a hardening of the override, not a substitute for the SLA/escalation path ordinary latency still needs (Open Question §1).
4. Build the module-activation lifecycle, reusing `template-lifecycle`'s stored-procedure + audit-trail pattern (`promote_template_status`, `template_status_history`) as the template — including that any config/control change on an `active` module transitions it to `pending-re-approval`, and that module status **and the underlying config/control data that drives drift detection** are writable only through this state machine (no direct column writes to either).
5. Wire a DRACO board review to run automatically when a module enters `pending-department-approval`, and make the attestation record the DRACO verdict ID as a required field rather than a display-only artifact. A blocking/REJECT verdict routes through item 3's override path (functionalOwner-member second approver + justification) rather than being overridable by a single sign-off. The attestation must record acceptance/override status per individual DRACO finding, not only the aggregate verdict ID, grouped by risk/control category to keep this usable rather than a wall of individual checkboxes.
6. Extend `governance_ledger` with `prev_hash`/`hash` hash-chaining, matching `audit_log`'s existing trigger-based implementation, or route activation decisions through `audit_log` directly. Audit that no code path can change module status outside item 4's state machine, since hash-chaining proves integrity of recorded entries, not completeness of what gets recorded. Add a periodic reconciliation job comparing live activation state against ledger entries as an independent detective check, not a substitute for the write-path lockdown. The reconciliation additionally compares a content hash of live config/control data against the hash recorded at last approval, not only presence of a ledger entry.
7. Wire `Ledger.razor` / `RPASGovernanceCenter.razor` (or a new approval-queue page) to actually call the endpoints from items 3–6 — currently every action button in the Governor Portal is decorative.
8. **Make partial delivery technically impossible to mistake for enforcement, not just documented as such.** The `active`-transition stored procedure requires `functional_owner_department` `NOT NULL` with no default, so activation cannot complete — a hard failure, not a policy reminder — until items 1–2 exist and are populated. Pair with a visible "gate not yet enforced" state in the portal for operator clarity, but the DB constraint is what actually does the work.
