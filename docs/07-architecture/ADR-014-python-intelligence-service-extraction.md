# ADR 014: Extracting AI-Foundry-Projects/pmbok into a Standalone Python Intelligence Service

## 1. Status

**Proposed (2026-07-19)**

Deciders: Owner(s) of `orchestrator/Adpa.Orchestrator` (the `IntelligenceClient`/`RitualController` integration), owner(s) of `AI-Foundry-Projects/pmbok`, and owner(s) of the Express document-generation pipeline (`server/src/modules/ai/`, `server/src/modules/multiStageDocumentProcessor/`).

## 2. Context

**Operational trigger.** The TypeScript backend is currently failing to complete document-generation jobs and running out of resources (reported 2026-07-19). This is no longer asserted without backing: see [DOCUMENT_GENERATION_RESOURCE_EXHAUSTION_RCA.md](DOCUMENT_GENERATION_RESOURCE_EXHAUSTION_RCA.md) for the investigation. Confirmed by the user: the frontend runs on Vercel and the backend on Render's **free tier** (512 MB RAM, spins down on inactivity) — `apphosting.yaml`'s Azure Container Apps hostname, referenced in an earlier version of the RCA, is stale and unrelated to the live deployment. The RCA's confirmed root cause is the Render free-tier ceiling itself, likely compounded by the code's `ADPA_PROCESS_ROLE=api`/`worker` split (`processRole.ts`, `server/src/worker.ts`) not being used — the backend reads as a single Render service, meaning (if `ADPA_PROCESS_ROLE` isn't explicitly set) API serving and every Bull/RabbitMQ queue consumer share one 512 MB process. The RCA explicitly does **not** recommend this ADR's extraction as the first fix — moving off the free tier and/or splitting API and worker into separate Render services is cheaper and should be tried first. What this ADR changes if that's insufficient: today, all LLM call orchestration for document generation (multi-provider dispatch/fallback in `server/src/modules/ai/` — `azure.ts`, `openai.ts`, `google.ts`, `mistral.ts`, `ollama.ts`, `FallbackExecutor.ts` — invoked from `multiStageDocumentProcessor`) runs inside the Node API/worker process regardless of how `ADPA_PROCESS_ROLE` is split or what Render plan is used; a separate, independently-scalable Python process removes that workload from the Node process's resource budget entirely, rather than just relocating or upsizing it.

**A parallel Python backend already exists, and a wiring point for it already exists — but they don't match.**

- `AI-Foundry-Projects/pmbok` (`pyproject.toml`) is a real FastAPI/Pydantic/SQLAlchemy package — "Idea-to-Reality PMBOK System" — implementing a 49-process PMBOK state machine (`pmbok/orchestrator/orchestrator.py`: `PMBOKOrchestrator`) with tenacity retry, an `asyncio.Semaphore(3)` concurrency throttle on LLM calls, and quality-gate-triggered regeneration (`_apply_quality_gate`/`_regenerate_with_improvements`). It persists to its own local `StateStore` (SQLite) and `ArtifactStore` (filesystem, under `settings.STORAGE_PATH`) — durable state it owns itself.
- Its FastAPI app (`pmbok/api/app.py`) exposes a session-based contract: `POST /sessions`, `POST /sessions/{id}/inputs`, `POST /sessions/{id}/process`, `POST /gates/{run_id}/{gate_name}/approve|reject`, `GET /runs/{run_id}/status|report|artifacts/{process_id}`. Sessions live in an in-memory `dict` (`_sessions`, `app.py:37`) — single-process, not restart-safe. There is no `/health` route and no `/rituals/*` route.
- `orchestrator/Adpa.Orchestrator/Clients/IntelligenceClient.cs` already exists and expects a *different* contract: `GET /health`, `POST /rituals/phase0/ingest`, `POST /rituals/phase0/business-case`, `POST /rituals/rtm/research-advice`, `POST /rituals/msrf/validate`. It's consumed today by `RitualController.cs`, which calls it and then persists the returned `IdeationSummary`/`BusinessCase`/`MsrfEvaluation`/`ResearchAdvice` into the Governance Ledger via `GovernanceDbContext` (e.g. `db.BusinessCases.Update(businessCase); await db.SaveChangesAsync();`, `RitualController.cs:140-141`) — i.e. the .NET side already treats the Python service as advisory-only and itself owns persistence, consistent with root `CLAUDE.md`'s Intelligence Tier rule ("Returns advisory JSON only; never mutates state").
- `orchestrator/Adpa.Orchestrator/Program.cs:102-106` already wires `IntelligenceClient` to an `INTELLIGENCE_URL` config key, defaulting to `http://intelligence` — a service-discovery-style hostname, not a monorepo-relative path.
- `orchestrator/Adpa.AppHost/Program.cs:32-54` has a fully-written but **commented-out** Aspire resource block titled "Intelligence Tier (Python FastAPI Service)", with the note `// Temporarily disabled until AI-Foundry-Projects is migrated to ADPA`. It launches `uvicorn main:app` from `../../AI-Foundry-Projects/services/intelligence` — a path that **does not exist** (only `AI-Foundry-Projects/pmbok` exists; there is no `AI-Foundry-Projects/services/` directory). The commented block also does `intelligence.WithReference(governanceDb)` and `intelligence.WithReference(messaging)` (RabbitMQ), and `apiservice.WithReference(intelligence...)`/`apiservice.WithEnvironment("INTELLIGENCE_URL", ...)` are commented out too.
- `orchestrator/Adpa.Orchestrator/Pmbok/Pmbok6ProcessCatalog.cs` independently mirrors the PMBOK process/dependency graph in C#, with a doc comment stating its "Source of truth is aligned with `AI-Foundry-Projects/pmbok/process_registry.py`" — further confirming the .NET side already treats `pmbok` (not a hypothetical future service) as the canonical intelligence backend, just not yet reachable.
- RabbitMQ ("messaging") is provisioned in Aspire (`Adpa.AppHost/Program.cs:26`), but MassTransit is not actually implemented anywhere in `Adpa.Orchestrator` — the only two hits for "MassTransit" in that project are the Aspire resource name and a comment in `RitualController.cs` (`system/health`: `"would normally check MassTransit bus health"`). There is no consumer or producer today.
- On the Node side, "regenerate when something changes" already exists as governed-feature packets — `document-dependency-graph` and `cascading-regeneration` (`server/governed-features.manifest.json`) — built on the existing Bull/Redis queue infrastructure. That mechanism is scoped to document edits made through the Express/Next.js path and is untouched by this ADR.

**Scope boundary.** This ADR covers two things that are currently unimplemented, not the Node document-editing regeneration path (which already works): (1) making the Python backend in `AI-Foundry-Projects/pmbok` actually reachable as a real service satisfying the contract `IntelligenceClient.cs` already expects, and (2) extending that same service to take over the LLM-orchestration step of document generation currently done in-process in the Node backend, to relieve its resource load. It does not change context-gathering, QA, or export stages of `multiStageDocumentProcessor`, and it does not touch RTM/document-dependency-graph logic already living in Postgres/Node.

## 3. Decision

**D1 — Extract to a separate repository, not `AI-Foundry-Projects/services/intelligence` in-monorepo.** The Python backend becomes its own repository (working name: `adpa-intelligence`), built from the existing `pmbok/` package (orchestrator, agents, engines, schemas, quality-gate/regeneration logic are reused as-is). This is the option the existing code already half-assumes: `INTELLIGENCE_URL` defaulting to `http://intelligence` (`Program.cs:104`) is a network-hostname default, not a monorepo-relative one, and the commented Aspire block's `../../AI-Foundry-Projects/services/intelligence` path was never realized. Splitting the repo avoids forcing a third build toolchain (pip/uv) into the pnpm+dotnet CI this monorepo already runs, and gives the Python service its own versioning, CI, and deploy cadence independent of frontend/orchestrator release cycles.

**D2 — The FastAPI contract is the integration boundary; the new repo's local stores are never read by ADPA.** The new repo must implement the contract `IntelligenceClient.cs` already expects (`GET /health`, `POST /rituals/phase0/ingest`, `POST /rituals/phase0/business-case`, `POST /rituals/rtm/research-advice`, `POST /rituals/msrf/validate`) — `pmbok/api/app.py`'s current session-based routes are superseded, not reused as-is. `StateStore`/`ArtifactStore` (SQLite/filesystem) remain internal working state for in-flight orchestration only — never the system of record. The Governance Ledger (Postgres, via `Adpa.Orchestrator`) and the Node backend's Postgres JSONB document storage stay authoritative, exactly matching the "advisory JSON only; never mutates state" rule in root `CLAUDE.md` and the pattern `RitualController.cs` already follows (call `intelligence.*Async()`, then persist the returned object itself).

**D3 — Document-generation LLM orchestration moves behind the same service, as a fallback if the Render fix (RCA §6) isn't sufficient.** The contract in D2 is extended with a generation/regeneration endpoint for the Node backend to call from its Bull worker (`worker.ts`) instead of invoking `server/src/modules/ai/` in-process. The worker's job stays the unit of durable, retryable work (no change to Bull/Redis); what changes is that the worker becomes a thin dispatcher — submit a generation request, await the advisory JSON/Markdown result, hand it to the existing persistence path — rather than performing multi-provider LLM calls and retries itself inside the Node process. This is a structural fix, not a substitute for fixing the Render deployment first: it removes the heavy, concurrency-sensitive work (multi-provider fallback, retries, the `asyncio.Semaphore(3)`-style throttling `pmbok/orchestrator/orchestrator.py` already implements) from Render's process entirely, rather than just fitting it under a bigger Render plan.

**D4 — RabbitMQ becomes the trigger transport specifically for governance-ritual-driven regeneration.** For changes that originate in the Governance Ledger (RTM amendments, business case revision, etc. — the `.NET` side, where RabbitMQ is already provisioned though unused), publish a change event that the new Python repo consumes to kick off its existing regeneration path (`_apply_quality_gate`/`_regenerate_with_improvements`). This is additive to, not a replacement for, the Node-side Bull-based `document-dependency-graph`/`cascading-regeneration` packets, which keep handling regeneration triggered by edits made through the Express/Next.js document path. The two trigger sources stay separate because they originate in different tiers with different systems of record.

**D5 — Aspire wiring is updated, not left commented out.** Once the new repo exists and exposes the D2/D3 contract, `Adpa.AppHost/Program.cs`'s intelligence block is replaced (not merely uncommented, since the `AddExecutable(..., "../../AI-Foundry-Projects/services/intelligence", ...)` path assumed monorepo colocation that D1 rules out) with a resource pointing at wherever the new repo is run for local dev — see Consequences for the open question this leaves.

## 4. Options Considered

**A — Migrate in-repo to `AI-Foundry-Projects/services/intelligence`** (i.e., just fix the path the commented Aspire block already names, keep it in this monorepo). *Rejected.* Matches the path that's already written, but adds a third build toolchain (pip) to pnpm+dotnet CI, ties the Python service's release cadence to the monorepo's, and doesn't change the fact that `INTELLIGENCE_URL`'s hostname-style default already assumes an independently-run service.

**B — Separate repository + HTTP integration over the existing `IntelligenceClient`/`INTELLIGENCE_URL` contract.** *Chosen (D1–D5 above).* Matches what the existing (disabled) integration code already assumes about deployment shape, and cleanly separates the Python toolchain's CI/CD from the rest of the monorepo.

**C — Defer the repo split; stabilize the contract in-monorepo first, extract later.** *Rejected.* Would mean building out the contract twice — once against a monorepo path, once against a real deploy target — for no benefit over doing the extraction now, given `INTELLIGENCE_URL` and `Pmbok6ProcessCatalog.cs`'s "aligned with `AI-Foundry-Projects/pmbok`" comment already point at treating it as an external, canonical service.

## 5. Consequences

- The four `/rituals/*` + `/health` routes must be implemented in the new repo before `Adpa.AppHost`'s Aspire wiring can be re-enabled — until then, `RitualController.cs`'s existing `intelligence.*Async()` calls continue to fail against nothing (there's no evidence they've ever succeeded against `pmbok/api/app.py`'s current, incompatible routes).
- D3 requires a new TypeScript client (an `IntelligenceClient.cs` analog) in `server/src/modules/ai/` or the worker, and a decision — not made here — about whether it fully replaces or runs alongside `FallbackExecutor.ts`'s existing multi-provider fallback for document types not yet migrated. Recommend a feature-flagged, per-document-type cutover rather than a single flag-day.
- Open question, not resolved by this ADR: how local dev launches the new repo once it's no longer at a monorepo-relative path. Candidates include a git submodule, a published dev container image, or a documented "run it separately and point `INTELLIGENCE_URL` at it" workflow (closest to today's `INTELLIGENCE_URL` default). Needs a short follow-up decision before D5 lands.
- The new repo needs its own CI/CD pipeline and a versioned contract (OpenAPI schema checked into or published from the new repo) so `IntelligenceClient.cs` and any new TS client don't silently drift from what the Python service actually serves — there's no such check today.
- Per root `CLAUDE.md`'s Governed Feature Loop, any non-trivial code touching `server/` or `orchestrator/` to consume the new service (the D3 TS client, the D4 RabbitMQ consumer wiring in `Adpa.Orchestrator`) still needs a `server/governed-features.manifest.json` entry and Contract Guards written first — the fact that the core LLM-orchestration logic moves to an external repo doesn't exempt the ADPA-side integration code from that process.
- D4's RabbitMQ path requires MassTransit actually being implemented in `Adpa.Orchestrator` (today it's provisioned infrastructure with no consumer/producer) — that's new work, not a wiring change.
- Extracting the repo does not, by itself, prove the resource-exhaustion report is resolved. Per the RCA linked in §2, the cheaper fix (moving the Render backend off the free tier and/or splitting API and worker into separate Render services) should be tried and measured first; D3 is the fallback if failures persist after that, not the first move.
