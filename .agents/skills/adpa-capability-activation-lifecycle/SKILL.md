# ADPA Capability Activation Lifecycle

## Purpose

`capability_registry` rows move through a real state machine — `draft → pending_department_approval → active → pending_re_approval → disabled` — instead of being a feature-flag-style toggle. Every transition is written through one stored procedure, `promote_capability_status`, which is also the only place a transition can be attempted, validated, and recorded (`capability_activation_history`) — modeled on `template-lifecycle`'s `promote_template_status` / `template_status_history` pattern (`server/migrations/000_baseline.sql` ~13036-13146 / ~7769-7781), with one deliberate deviation (see next section). Phase 4 layers a DRACO verdict gate onto the same procedure's `→active` path. Phase 5 adds tamper-evidence: `capability_activation_history` itself is now append-only-locked, a reconciliation sweep detects drift between `capability_registry.activation_status` and the history table, and both scheduled jobs record heartbeats so a silently-stopped detective control is itself detectable. Phase 7 adds a third gate on the same procedure: a transition to `pending_department_approval`/`active` now also requires the resolved `functional_owner_department` to have at least one active `user_departments` member in the capability's own `portfolio_id`.

**Phase 2 task 4 and Phase 3 task 6** (2026-07-13) close the two things Phase 7's gate implied but didn't itself build: a legitimate way *through* the gate when the normal single-approver path can't proceed. **Phase 2 task 4** is a two-distinct-department-member override (`capability_override_requests`, migration 440) — deliberately built **Node-side, not in the .NET orchestrator's `TaskApprovalGate`**, correcting the implementation plan's literal text: confirmed before implementation that `TaskApprovalGate` has zero connection to `capability_registry` writes (it only reads via `CapabilityRegistryClient.GetAsync` to gate the unrelated `BusinessCase`/`RtmAmendment` ritual flow), while Node already owns `promote_capability_status`, `user_departments`, and `users` — no cross-tier hop needed. **Phase 3 task 6** is the break-glass substitute for when the department has fewer than two active members at all (`capability_override_exceptions` / `override_exception_reviews`, migration 441) — a five-party review (account_owner, manager, internal_audit, external_auditor, super_admin), request-then-pickup, only a Super Admin's own activation fires the transition. See [Phase 2 task 4](../../../docs/superpowers/specs/2026-07-13-federated-capability-ownership-phase2task4-design.md) and [Phase 3 task 6](../../../docs/superpowers/specs/2026-07-13-federated-capability-ownership-phase3task6-design.md) design specs for the full reasoning, alongside [Phase 3](../../../docs/superpowers/specs/2026-07-11-federated-capability-ownership-phase3-design.md), [Phase 4](../../../docs/superpowers/specs/2026-07-12-federated-capability-ownership-phase4-design.md), [Phase 5](../../../docs/superpowers/specs/2026-07-12-federated-capability-ownership-phase5-design.md), and [Phase 7](../../../docs/superpowers/specs/2026-07-12-federated-capability-ownership-phase7-design.md), and [the implementation plan](../../../docs/implementation/FEDERATED_CAPABILITY_OWNERSHIP_IMPLEMENTATION_PLAN.md#phase-3-action-item-4-module-activation-lifecycle).

**Two bugs found and fixed while verifying Phase 3 task 6 end-to-end against real Postgres** (both are why migrations 442 and 443 exist, on top of 439's transition graph — see their own headers for full reasoning):
1. The transition graph (435/439) didn't allow `draft → disabled` — a break-glass decline against a still-`draft` capability (never yet submitted for approval) failed with "illegal activation_status transition." Migration 442 adds it as a narrow, deliberate extension, not a general loosening.
2. Phase 7's active-member gate applied unconditionally, including to break-glass's own `activate` call — meaning the exact zero/one-member scenario break-glass exists to handle was itself blocked by the gate it was supposed to route around. Migration 443 adds `p_bypass_deadlock_gate boolean DEFAULT false` to `promote_capability_status`, defaulted false for every existing caller, and set `true` only by `CapabilityOverrideExceptionController.activate` (itself already gated to `super_admin`/`admin`).

**ADR-012 PR6a addition (2026-07-17, shipped)**: `capability_override_requests.status` (and its accompanying decision columns) has never been DB-enforced the way `activation_status` is — `markApproved`/`markDenied` are today plain app-layer `UPDATE`s with no procedure to extend. Migration 445 adds `decide_capability_request(request_id, decision, decided_by, decided_by_department, reason, override_expires_at)`, `decision IN ('approved', 'denied', 'withdrawn')`, intended to become the sole permitted writer (PR6c makes that real). `SECURITY DEFINER` + a pinned `search_path`, so it keeps working once PR6c's guard is enforcing. Withdraw is a genuinely different rule from approve/deny, not a variant of the same one: requester-only (`decided_by = requested_by`), no department check at all; approve/deny require `decided_by != requested_by` **and** an active `user_departments` membership in `decided_by_department` for the capability's own `portfolio_id` — the same two-distinct-department-member rule the app layer already enforces (Phase 2 task 4), now also enforced here as defense in depth, matching this skill's own established "the app layer checks this too, but a DB-level guarantee means a future code path can't accidentally skip it" reasoning. Performs its own `audit_log` insert via `capability_row_digest` (migration 444, PR3) — digest only, never the raw `justification`. **This PR is purely additive**: `markApproved`/`markDenied` don't call it yet (PR6b), and nothing guards direct `UPDATE`s yet (PR6c) — the procedure exists and is correct, but isn't yet the only path.

**Correction carried from ADR-012 §D (caught during this PR's own implementation)**: an earlier draft of ADR-012 planned PR6c's lockdown as `REVOKE UPDATE ... FROM <app role>`. That's wrong for this codebase specifically — see this skill's own invariant below (unchanged, just newly relevant to a second table): there is no separate low-privilege app role to revoke from without rewiring deployment credentials. PR6c instead adds a second `BEFORE UPDATE` trigger + guard variable, structurally identical to `guard_capability_registry_activation_status`, just guarding `capability_override_requests`'s decision columns instead of `capability_registry.activation_status`.

**Verification gap (same shape as PR2/PR3)**: `server/tests/integration/`'s shared harness is still blocked repo-wide. `server/scripts/verify-decide-capability-request.ts` is the standalone-script fallback (same precedent this skill's own Phase 6/7 real-Postgres proofs already used for this exact blocker) — transaction-wrapped, always `ROLLBACK`'d, safe to run repeatedly against a real database including this project's persistent Azure dev instance. Written and type-checked in this session but **not executed against a live database** — deliberately left for the project owner to run (`cd server && npx tsx --require dotenv/config scripts/verify-decide-capability-request.ts`) rather than run unilaterally against shared infrastructure outside an explicit request to do so.

**PR6a review-finding fixes (2026-07-18)**: three genuine issues from a second-pass code review, fixed directly rather than deferred:
1. **Authorization bound to the caller's claim, not the capability's real department**: the original active-membership check verified `p_decided_by` against whatever `p_decided_by_department` the caller supplied — a member of `Legal` could pass `'Legal'` as `p_decided_by_department` and be accepted as a valid approver for a `Compliance`-owned capability, since nothing tied the check to the capability's own `functional_owner_department`. The procedure now resolves the capability's real `functional_owner_department` itself and requires `p_decided_by_department` to match it (rejecting a mismatch with a specific error) **before** checking membership — the app layer's existing callers already pass the correct value, so this is purely a closed gap, not a behavior change for legitimate callers. Matters more once PR6c makes this procedure the sole writer: at that point, "defense in depth" has to mean binding to the actual authorization boundary, not merely trusting an argument a direct caller could set to anything.
2. **NULL decision silently fell through as 'withdrawn'**: `p_decision NOT IN ('approved', 'denied', 'withdrawn')` evaluates to `NULL` (not `TRUE`) when `p_decision IS NULL`, so the intended reject-invalid-decision guard never fired for a NULL input — execution reached the final `ELSE` branch of the decision dispatch and treated a NULL decision as `'withdrawn'`. Added an explicit `p_decision IS NULL OR ...` check.
3. **`verify-decide-capability-request.ts` couldn't actually run its own negative cases**: the whole script runs inside one outer transaction (always `ROLLBACK`'d at the end), but each expected-failure case just caught the error with a bare `try`/`catch` — Postgres aborts the *entire* transaction on the first error, so every statement after the first expected failure (including the next case's own `createRequest()`) failed with "current transaction is aborted" instead of running at all. `expectThrows` now wraps each case in its own `SAVEPOINT`/`ROLLBACK TO SAVEPOINT`, containing the abort to just that case. This was a real gap in every "verified via this script" claim made in this session — the script had never actually been able to reach most of its own negative-case assertions, only the first one. Two new cases (REQ-CAP-6A-008/009) cover the two fixes above.

**ADR-012 PR6b addition (2026-07-17, shipped)**: `CapabilityOverrideRequestRepository.markApproved`/`markDenied` now delegate entirely to `decide_capability_request` (PR6a) — each is a single `this.pool.query('SELECT decide_capability_request(...)', [...])` call, with the TS-managed transaction/`insertAuditLogDigest` machinery PR3 gave them removed outright, since the procedure now performs its own `UPDATE` and its own `audit_log` insert atomically in one DB call. `create()` is untouched (still PR3's transaction+`insertAuditLogDigest` pattern — request *creation* isn't a "decision" the procedure covers). Deliberately landed with `UPDATE` still functionally reachable (PR6c's guard trigger isn't active yet) so this refactor is revertible on its own if it surfaces a regression, isolated from the lockdown step. The existing `capabilityOverrideAuditCoverage.test.ts` white-box tests for these two methods were rewritten, not left "unchanged" in the literal sense — they asserted the *old* `BEGIN`/`UPDATE`/`INSERT INTO audit_log`/`COMMIT` SQL sequence, which no longer exists; the new REQ-CAP-013 tests assert the new single-call shape while still proving the same behavioral guarantee this Action Item cares about (the write and its audit entry happen atomically, now enforced one layer deeper, inside the procedure itself rather than orchestrated from TS).

**PR6b review-finding fix (2026-07-18): approval atomicity.** `CapabilityOverrideController.approve` called `promote_capability_status` and `markApproved` (→ `decide_capability_request`) as two separate autocommit statements — flagged independently across four PRs (#742, #744, #746, #748) as the single most repeated finding in this session's review pass. A failure between the two calls (or a concurrent `withdraw()` racing in) could leave the capability transitioned with its request still `pending`/`withdrawn`, or vice versa. Fixed by giving `markApproved` an optional fifth `runner` parameter (`Pick<Pool, 'query'>`, defaults to `this.pool` so every other caller is unaffected) and having `approve()` acquire one client, `BEGIN`, run both `promote_capability_status` and `markApproved(..., client)` on that same client, then `COMMIT`/`ROLLBACK` around both together. This also closes PR748's specific withdraw-vs-approve race as a side effect, without touching `withdraw()` itself: `decide_capability_request`'s own `SELECT ... FOR UPDATE` (migration 445) now holds the request-row lock for the *whole* transaction's duration, not just its own statement, so a concurrent `withdraw()` blocks until `approve()`'s transaction resolves, then correctly fails on the now-decided row instead of racing it — the losing side gets a clean rejection, not silent double-writes. Also extended `approve()`'s known-rejection classification (`isKnownRejection`) to include `decide_capability_request`'s "has already been decided"/department-mismatch messages, so a losing concurrent decision surfaces as `400` (a real conflict), not a raw `500`. New contract guard, REQ-CAP-016 (`overrideApprovalAtomicity.test.ts`) — mocks `pool.connect()` and asserts both writes land on the same client inside one `BEGIN`/`COMMIT`, and that a failure anywhere rolls back both and still releases the client. `deny()`/`withdraw()` were not touched — each only ever makes one write, so this specific two-writes-not-atomic gap doesn't apply to them.

**ADR-012 PR6c addition (2026-07-18, shipped)**: migration 446 is the one-way door — `guard_capability_override_requests_decision_columns()`, a `BEFORE UPDATE` trigger checking whether any of `status`/`approved_by`/`approved_by_department`/`decided_at`/`denial_reason`/`withdrawn_at`/`override_expires_at` changed, `RAISE EXCEPTION` if so unless `current_setting('adpa.allow_capability_override_decision_write', true) = 'on'` — structurally identical to `guard_capability_registry_activation_status`, guarding a group of seven columns instead of one (they only ever change together as part of one decision; a partial guard would leave a side door). `decide_capability_request` is redefined (not a new function — `CREATE OR REPLACE`, migration 436's redefinition pattern) to `set_config(..., 'on', true)` immediately before its own `UPDATE` and back to `'off'` immediately after, mirroring `promote_capability_status`'s own "close the bypass window right after the one sanctioned write" reasoning exactly. **Must-verify subtlety this packet's own invariants don't yet call out explicitly**: the trigger fires even for `UPDATE`s issued from *inside* `decide_capability_request` itself — it's a row-level trigger with no awareness of its own caller — so forgetting the guard-variable set/reset around the procedure's own `UPDATE` would make the procedure lock itself out. `verify-decide-capability-request.ts`'s REQ-CAP-6C-004 exists specifically to catch that class of mistake (calls the procedure again after the trigger is active, confirms it still succeeds), not just the more obvious "direct UPDATE gets rejected" case.

## Invariants

- Must always: change `activation_status` only through `promote_capability_status(p_capability_id, p_new_status, p_changed_by, p_reason, p_draco_verdict_id, p_is_override, p_override_expires_at)`. There is no other sanctioned write path.
- Must never: assume `template-lifecycle`'s lockdown pattern is a `REVOKE`-based DB-privilege separation — it isn't, in this codebase or in this feature. `000_baseline.sql` and every migration were grepped for `REVOKE`: zero hits. This app also connects to Postgres via one `DATABASE_URL`/role for both migrations and runtime — there's no separate low-privilege app role to revoke from without rewiring deployment credentials. This packet's lockdown is a `BEFORE UPDATE` trigger (`guard_capability_registry_activation_status`) checking a session-local guard variable (`current_setting('adpa.allow_activation_status_write', true)`) that only `promote_capability_status` sets.
- Must never (review finding, PR #747, corrects an earlier overclaim in this same invariant): describe the session-guard-variable pattern (`guard_capability_registry_activation_status` or `guard_capability_override_requests_decision_columns`) as unbypassable or equivalent to a real privilege boundary. Any caller holding this app's own `DATABASE_URL` role can set the guard variable itself (`SELECT set_config('adpa.allow_...', 'on', true)`) and then issue a raw `UPDATE`, since the trigger has no way to distinguish "the procedure set this" from "a caller set this directly." The guard protects against an *accidental* direct write from a code path that doesn't know to route through the procedure — the actual failure mode this codebase has hit before — not against a caller with equivalent database privileges deliberately working around it. Closing that gap for real would mean a separate low-privilege application role with `UPDATE` revoked and only `EXECUTE` granted on the procedure, already ruled out for this codebase's single-role deployment (see the invariant above) — accept the trade-off explicitly rather than mis-describing what the trigger actually defends against.
- Must always: keep the transition graph in `promote_capability_status` exactly as narrow as the plan's stated flow — `draft→{pending_department_approval}`, `pending_department_approval→{active,disabled}`, `active→{pending_re_approval,disabled}`, `pending_re_approval→{active,disabled}`, `disabled→{}` (terminal). Phase 4's DRACO gate and Phase 7's `functional_owner_department NOT NULL`/active-member precondition extend this same procedure's validation step — they do not bypass it or duplicate the transition graph elsewhere.
- Must always (Phase 7): check the transition graph, then the active-member gate, then the DRACO verdict gate, in that order — an illegal transition fails with its own specific message before either newer check runs; "is there anyone who could approve this" is a more fundamental precondition than "did the specific evidence pass review."
- Must always (Phase 7): scope the active-member check to `pending_department_approval`/`active` only, never `disabled` — a module whose department has zero active members in this portfolio must still be shuttable. Gating `disabled` too would trap a module in its current state exactly when its accountable department disappears, which is the opposite of the intended effect.
- Must never (Phase 7): let the Phase 6 admin-role bypass (`CapabilityRegistryController.promote`, app layer) substitute for this DB-level check. The admin bypass answers "does this caller need to prove their own department membership to invoke the endpoint" (no); this gate answers "does the target department have anyone active in this portfolio at all" (a separate, structural question). An admin can promote a `Compliance`-owned module if some Compliance member — not necessarily the admin — is active in that portfolio; an admin cannot force a promotion into a portfolio where the department has zero active members, because that is the exact deadlock this gate exists to catch regardless of who is asking.
- Must always (Phase 4): require `p_draco_verdict_id` to be non-null **and** resolve to a real `draco_reviews` row for any transition to `active` — `capability_activation_history.draco_verdict_id` has a real FK to `draco_reviews(id)` (migration 436) so this is enforced at INSERT time too, but the procedure checks explicitly first for a clear exception message rather than a raw FK-violation.
- Must always (Phase 4): require an override (`p_is_override = true`, non-empty `p_reason`, non-null `p_override_expires_at`) for **both** `CONDITIONAL_PASS` and `REJECT` verdicts, not `REJECT` alone — confirmed against `dracoVerdictEngine.ts`'s `buildPublicationAdvisory` that `CONDITIONAL_PASS` sets `advisable_to_publish: true` while still carrying unresolved `conditions_for_approval`, and confirmed against `server/src/routes/approvals.ts:141-176` that the existing document-approval DRACO gate has exactly this gap today (checks `REJECT` only) — this procedure closes it for capability activation, it does not fix `approvals.ts`.
- Must never (Phase 4): treat this procedure's override check as authorization. It only verifies an override was *recorded* (flag + justification + expiry) — it does not verify *who* recorded it or their department membership. **Resolved**: that authorization layer is `CapabilityOverrideController`/`CapabilityOverrideExceptionController` (Phase 2 task 4 / Phase 3 task 6, Node-side, not the orchestrator's `TaskApprovalGate` — see this skill's Purpose section for why), the same "NOT NULL is a backstop, not the validator" pattern the plan's Open Question §4 already flagged for Phase 7's precondition.
- Must always: reset the session guard to `'off'` immediately after `promote_capability_status`'s own `UPDATE`, not leave it `'on'` for the rest of the calling transaction — `set_config(..., true)` (is_local) only reverts at transaction end by default, and closing the window right after the one sanctioned write is what keeps a same-transaction raw `UPDATE` piggyback from also slipping through.
- Must always: treat the drift mechanism as opt-in, metadata-driven infrastructure, not a mechanism tied to any specific existing module — `module_drift_sources` starts empty because no governed module currently has a config/control table wired into this system. A table adopts drift detection by calling `attach_module_drift_trigger(module_id, table_name, monitored_columns)`; it must carry `module_id`/`portfolio_id` columns matching `capability_registry`'s own scoping (by convention — there is no other precedent to match against yet).
- Must always: build dynamic trigger/column SQL in `attach_module_drift_trigger` using `format()`'s `%I` (identifier quoting) and `quote_ident()` per column — never string-concatenate a caller-supplied table/column name into executable SQL.
- Must always: rely on `AFTER UPDATE OF <monitored_columns>` (native Postgres column-filtered trigger firing) for "don't fire on metadata-only writes" — this is simpler than, and equivalent to, a manual `WHEN` clause comparing OLD/NEW per excluded column.
- Must always: no-op the drift trigger (not error) when the matching `capability_registry` row isn't currently `active`, or when the row doesn't carry a resolvable `module_id`/`portfolio_id` pair — a config edit on a non-active module isn't a failure worth surfacing here.
- Must always (Phase 2 task 4): require a SECOND, DISTINCT active department member to approve/deny an override request — never the same person who created it. Enforced at both layers: the app layer compares caller identity to `requested_by` explicitly, and `capability_override_requests` has `CHECK (approved_by IS DISTINCT FROM requested_by)` as a DB-level backstop. No admin bypass on either step, unlike the plain `promote` endpoint — the entire point is two genuine department signatures. If the department has fewer than two active members, `approve` always 403s for lack of a distinct member — this is the intended funnel into Phase 3 task 6's break-glass path, not a bug to fix.
- Must always (Phase 3 task 6): enforce the deadlock precondition (department has <2 active members in this portfolio) via a `BEFORE INSERT` trigger on `capability_override_exceptions` (`guard_capability_override_exception_requires_deadlock`), not just an app-layer check — this is specifically the deadlock substitute, never a general-purpose bypass of Phase 2 task 4's two-signature requirement.
- Must always (Phase 3 task 6): guarantee both consequences of a decline (disable the capability, mark the exception `disabled`) via a DB trigger (`guard_override_exception_review_decision`, `AFTER UPDATE OF decision`) — a future code path that writes `decision` directly can't skip either half. Escalation *notification* dispatch stays app-level (Postgres can't make outbound HTTP/SMTP calls; every other notification in this codebase already dispatches app-side).
- Must always (Phase 3 task 6): gate `CapabilityOverrideExceptionController.activate` to `super_admin`/`admin` only, checking `users.role` the same case-insensitive way as everywhere else in this codebase — raising an exception never itself activates anything (request-then-pickup).
- Must always (migration 443): pass `p_bypass_deadlock_gate = true` to `promote_capability_status` **only** from `CapabilityOverrideExceptionController.activate`, never from any other call site — every other caller (Phase 2 task 4's approval, the plain Phase 6 promote endpoint, both scheduled sweeps) must leave it at its `false` default, or Phase 7's active-member gate becomes meaningless.
- Must always (migration 442): treat `draft → disabled` as a legitimate, narrow addition to the transition graph (a module can be declared dead before ever being submitted for approval) — not a precedent for loosening the graph generally elsewhere.
- Must never: fold the attestation-lapse sweep's override-expiry half into this pass — `is_override`/`override_expires_at`/`warned_24h_at`/`warned_12h_at` columns exist on `capability_activation_history` (part of this packet's own schema). **Resolved**: Phase 2 task 4 is the first thing that sets `is_override = true`, so `overrideExpiryCheck.ts` / `runOverrideExpirySweep()` (in `capabilityAttestationJob.ts`, the *same* job, not a new one, per the plan's own framing) now reads it — reverting a lapsed override to `pending_re_approval` with no subsequent normal approval, and dispatching idempotent 24h/12h warnings via `warned_24h_at`/`warned_12h_at`.
- Must never: treat "shared-table storm" (one config-table change re-opening several modules' approvals at once) as N independent, unrelated transitions when investigating — it's visible today via `capability_activation_history` rows sharing a `changed_at`/reason; no separate alerting channel is wired (deferred hardening item, not core mechanism).
- Must always (Phase 5): treat `capability_activation_history` as append-only, full stop — `UPDATE`/`DELETE` are rejected unconditionally, even for `promote_capability_status` itself (there is no legitimate reason to ever modify or remove a written row). `INSERT` is gated by its own dedicated session-guard variable (`adpa.allow_activation_history_write`), separate from `activation_status`'s own guard (`adpa.allow_activation_status_write`) — the two can't share one variable because `promote_capability_status` resets the `activation_status` guard to `'off'` *before* its `INSERT` into this table runs.
- Must always (Phase 5): treat the reconciliation sweep (`activationHistoryReconciliation.ts`) and the append-only lockdown as deliberately redundant, not one-substitutes-for-the-other — the lockdown proves recorded entries weren't altered after the fact; the sweep is what would catch a hole in the lockdown itself that neither of us has thought of yet (a permission-model gap, a bug, a direct restore).
- Must never (Phase 5): treat a `draft` capability with no `capability_activation_history` row as drift — it's expected, since `draft` is the pre-promotion default. Every other status with no history row (or a history row whose `new_status` disagrees) is drift.
- Must always (Phase 5): record a heartbeat (`scheduled_job_heartbeats`, success or failure) on every run of both `capabilityAttestationJob` and `capabilityActivationReconciliationJob`. Liveness is cross-checked, not self-checked — `capabilityAttestationJob` checks the reconciliation job's staleness on its own hourly tick, rather than adding a third scheduled job whose own liveness would then need monitoring too.

## Interaction Rules

- Depends on: `adpa-capability-registry` (Phase 1 — the table this packet adds `activation_status` to, and Phase 7 — the owner-department values and the `departments`/`user_departments` tables this packet's new gate reads) and `adpa-task-approval-gate` (Phase 2 — the gate this state machine plugs into, per the plan's own sequencing note).
- Must not break: Phase 1's `capability_registry` row shape (`UNIQUE (module_id, portfolio_id)`, owner columns) — this packet only adds a column and a lockdown trigger, it doesn't change existing columns' semantics.
- **Resolved (was "new interaction tests required when Phase 7 lands")**: Phase 7 added the `functional_owner_department NOT NULL`/active-member precondition to `promote_capability_status`. Existing Phase 3/4 contract guards asserting "a legal, verdict-satisfying transition succeeds" were re-verified against the tightened precondition, not assumed to still pass — both `federated-capability-ownership-phase3.test.ts` and `-phase4.test.ts` needed real owner departments and, for any promote past `draft`, a matching active `user_departments` row added to their helpers. `federated-capability-ownership-phase6.test.ts`'s admin-bypass test needed correcting for the same reason (see this skill's Phase 7 invariant on the admin bypass above).
- New interaction tests required when: Phase 4 task 1 is eventually built — it must produce a `draco_reviews.id` this procedure's gate can consume as-is; no change to the gate itself should be needed, only to how a verdict ID gets created.
- **Resolved (was "new interaction tests required when Phase 2 task 4 / Phase 3 task 6 start setting is_override")**: both now do. Re-verified the append-only lockdown still permits `promote_capability_status`'s INSERT with `is_override`/`override_expires_at` populated — the standalone scratch verification script exercised this directly (approve → history row has `is_override=true` and a set expiry).
