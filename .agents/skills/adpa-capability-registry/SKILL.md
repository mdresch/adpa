# ADPA Capability Registry

## Purpose

Every governed module needs three declared owners (`platformOperator`, `functionalOwnerDepartment`, `controlDefinitionOwnerDepartment`) as a runtime-queryable, constraint-enforceable table — `capability_registry` — not just an entry in the build-time `governed-features.manifest.json`. This packet's current scope is the pure reconciliation contract: given the manifest's module ids, the current set of portfolio ids, and the registry's existing rows, decide which `(module_id, portfolio_id)` pairs are missing a row and which existing rows no longer correspond to anything in the manifest. See [the Phase 1 design spec](../../../docs/superpowers/specs/2026-07-10-federated-capability-ownership-phase1-design.md) and [the implementation plan](../../../docs/implementation/FEDERATED_CAPABILITY_OWNERSHIP_IMPLEMENTATION_PLAN.md#phase-1-action-item-2-capability-ownership-registry).

Sibling skill: [adpa-federated-capability-ownership](../adpa-federated-capability-ownership/SKILL.md) covers Phase 0 (department identity, Firebase claims sync, `companies.created_by`) under the same governed-feature packet.

This skill also now covers the read-only HTTP lookup (`CapabilityRegistryRepository`/`CapabilityRegistryController`, `GET /api/v1/capability-registry/:moduleId/:portfolioId`) that Phase 2's .NET `TaskApprovalGate` calls to resolve a module's declared owner — the orchestrator's `GovernanceDbContext` is a physically separate Postgres database (Aspire-provisioned `governance-ledger`) and cannot query `capability_registry` directly. See `adpa-task-approval-gate` for the orchestrator-side consumer.

**Phase 6 addition**: `POST /api/v1/capability-registry/:moduleId/:portfolioId/promote` — the first human-triggerable path to `promote_capability_status` anywhere in the codebase (previously only an automated cron job called it). Authenticated + department-membership/admin-authorized, unlike the sibling `GET`. See [the Phase 6 design spec](../../../docs/superpowers/specs/2026-07-12-federated-capability-ownership-phase6-design.md) and `adpa-capability-activation-lifecycle` for the stored procedure it calls.

**Phase 7 addition**: `functional_owner_department` is real, business-assigned data now, not a nullable placeholder — `moduleOwnerAssignments.ts` resolves each manifest packet to its owner (`compliance`/`template-lifecycle` → Compliance, `ip-governance` → Legal, everything else → IT, an honest default reflecting that most governed packets are pure platform engineering with no separate business owner), migration 438 backfilled every pre-existing row, and `seedCapabilityRegistry.ts` now resolves a real owner for every newly-inserted row going forward. Migration 439 makes this a schema-level guarantee (`NOT NULL` + FK to `departments`), not just an application default. See [the Phase 7 design spec](../../../docs/superpowers/specs/2026-07-12-federated-capability-ownership-phase7-design.md).

**Phase 2 task 4 / Phase 3 task 6 addition**: this module's `routes.ts` also mounts the override request/approve/deny flow (`.../override/*`) and the break-glass exception flow (`.../exceptions/*`) — both authenticated, both calling `promote_capability_status` on success. The controllers/repositories/schema for these live in this same `server/src/modules/capabilityRegistry/` directory (`CapabilityOverrideController`, `CapabilityOverrideExceptionController`, migrations 440-443), but the actual state-machine reasoning (why a second signature, why break-glass, why the deadlock gate) belongs to `adpa-capability-activation-lifecycle` — see that skill for the full detail; this skill just notes that the routes exist here.

**Orchestrator proxy addition (2026-07-13)**: all seven of these Node endpoints — `promote` plus the six override/exception ones above — are now proxied from the .NET orchestrator too, via `CapabilityController.cs`'s shared `Relay` helper and matching `CapabilityRegistryClient` methods (`RequestOverrideAsync`, `ApproveOverrideAsync`, `DenyOverrideAsync`, `RequestExceptionAsync`, `DecideExceptionReviewAsync`, `ActivateExceptionAsync`). This is what a Governor Portal page now has to call through once it has a real token to relay (see `adpa-governor-portal-auth`) — previously only `promote` had an orchestrator-side route at all.

**List-pending addition (2026-07-14)**: `GET .../overrides/pending` and `GET .../exceptions/pending` — the endpoints the Governor Portal's `/approvals` queue page actually needs, since every action endpoint above requires already knowing a `moduleId`/`portfolioId`/`requestId` a queue view can't assume. Both scoped by caller: admin sees everything, a plain user sees only what they could legitimately act on (own active department for overrides, named-reviewer-with-undecided-review for exceptions) — **two genuinely different authorization mechanisms, not one shared rule expressed twice** (corrected 2026-07-17 — see the ADR-012 PR2 addition below; an earlier version of this note implied they were the same logic). **Must always** register these two literal routes *before* the generic `GET /:moduleId/:portfolioId` in `routes.ts` — both are 2-segment GET paths, and Express matches in registration order; registered after, they'd be silently swallowed by the generic route instead. Proxied orchestrator-side via `CapabilityRegistryClient.ListPendingOverridesAsync`/`ListPendingExceptionsAsync` (a `GetRelayAsync` helper, deliberately not named `GetAsync` — that name already exists on the class with an incompatible-by-erasure overload).

**ADR-012 PR2 addition (2026-07-17, shipped)**: [ADR-012](../../../docs/07-architecture/ADR-012-capability-register-and-request-lifecycle.md) Action Item 2 extracted `overrides/pending`'s admin-sees-all/member-sees-own-active-department clause into `departmentScopedQuery.ts`'s `buildAdminOrActiveDepartmentMemberClause({ portfolioColumn, departmentColumn })` — a pure SQL-fragment builder, parameterized by which two columns to scope against, so PR4's new `GET /api/v1/capability-registry` list endpoint can reuse the identical admin-bypass-or-active-membership decision against `capability_registry.functional_owner_department` instead of `capability_override_requests.requested_by_department`, without a third hand-written copy. `CapabilityOverrideRequestRepository.listPendingForUser` now calls it (behavior-preserving — same generated SQL text and `$1`/`$2` = `isAdmin`/`userId` binding order as before extraction; verified unchanged by the existing real-Postgres integration test, `server/tests/integration/federated-capability-ownership-approvals-queue.test.ts`). **`CapabilityOverrideExceptionRepository.listPendingForUser` is explicitly not a consumer** — its non-admin branch authorizes by named-reviewer-assignment (`EXISTS` against `override_exception_reviews.reviewer_user_id`, no department check at all), a different, already-correct mechanism this Action Item does not touch. This correction was caught during PR2's own implementation: [ADR-012](../../../docs/07-architecture/ADR-012-capability-register-and-request-lifecycle.md) §A/§6 Item 2 originally (and wrongly) asserted both `listPending` methods shared the same predicate. **Hardening follow-up (review finding on PR #741)**: `buildAdminOrActiveDepartmentMemberClause` now validates both column arguments against a plain `identifier`/`alias.identifier` pattern before interpolating them, throwing rather than silently accepting anything else — CWE-89 defense-in-depth for a shared helper whose future callers aren't guaranteed to only ever pass hardcoded literals the way today's two do.

**ADR-012 PR4 addition (2026-07-17, shipped)**: `GET /api/v1/capability-registry` (no path segment, registered as `router.get('/', ...)`) — the Governor Portal's first browsable capability list, where before only the single-row internal lookup (`GET /:moduleId/:portfolioId`) and the seed/reconciliation scripts could enumerate rows at all. `CapabilityRegistryRepository.listForUser(userId, isAdmin)` reuses PR2's `buildAdminOrActiveDepartmentMemberClause` scoped by `functional_owner_department` (not `listAll()`, which stays unfiltered/reconciliation-only — feeding `reconcileCapabilityRegistry`, never a human-facing response). Proxied orchestrator-side via `CapabilityController.ListCapabilities` (`GET api/Capability`, no route segment — matches the controller's own `[Route("api/[controller]")]`) and `CapabilityRegistryClient.ListAsync`, same `GetRelayAsync`/`RelayList` shapes as every other cross-capability action in this file. Blazor: `Components/Pages/Capabilities.razor` at `/capabilities`, `[Authorize]`, one `GovernorCard` per capability with a `StatusChip` mapped from `activation_status` (`active`→Approved, `pending_department_approval`/`pending_re_approval`→Pending, `disabled`→Declined, `draft`/unknown→Neutral) — added to `MainLayout.razor`'s nav ahead of Approvals. **Action buttons render a status-aware label but are `Disabled="true"`** — PR5 wires them to the real `Promote`/`Request Override`/`Raise Break-Glass` endpoints, gated on the caller's department membership via PR1's `CurrentUserService`. This PR's formal dependency is PR2 only (not PR1), so it deliberately doesn't reach for `CurrentUserService` — the plan's own PR4 task explicitly allows shipping the actions disabled/absent if this PR lands before PR1/PR5 merge.

**ADR-012 PR5 addition (2026-07-17, shipped)**: makes `override/request`/`exceptions/request`/`promote` — three endpoints with zero UI callers until now — reachable from `Capabilities.razor`. One shared component, `Components/Shared/RequestActionForm.razor`, covers all three via a `Mode` parameter (`Promote`/`Override`/`BreakGlass`): `Promote` is one-step (it's an existing endpoint being wired up, not a "create action this ADR adds," so the two-step requirement doesn't apply to it — ADR-012's UI-requirements section scopes that to override/exception requests specifically); `Override`/`BreakGlass` are two-step draft→confirm, with `BreakGlass` additionally requiring a checked confirmation box on step 2 ("I confirm no eligible second approver exists...") — the deliberately-higher-friction treatment ADR-012 §B calls for. Justification/reason is validated client-side (the advance/submit button stays disabled while empty or whitespace-only) before any HTTP call. `AllowedNextStatuses(currentStatus)` in `Capabilities.razor` mirrors `promote_capability_status`'s transition graph exactly (`server/migrations/435_module_activation_lifecycle.sql`: `draft`→`pending_department_approval`; `pending_department_approval`/`pending_re_approval`→`active`/`disabled`; `active`→`pending_re_approval`/`disabled`; `disabled` terminal) — the UI never offers a target status the DB would reject, though the DB CHECK/procedure remains the actual enforcement point, not this client-side mirror. Action buttons only render when `CurrentUser.GetAsync()`'s resolved profile is admin or an active member of the capability's `functionalOwnerDepartment` — the exact gate ADR-012 exists to add; a card with zero legal next status (i.e. `disabled`) shows neither buttons nor a false promise of an action. **DTO extraction (blocking precondition, done first)**: `PendingOverride`/`PendingException`/`ExceptionReview` moved out of `Approvals.razor`'s private nested classes into `Models/CapabilityRequests.cs` (now globally imported via `_Imports.razor`, alongside `Adpa.Web.Services` for `CurrentUserService`/`ResolvedCurrentUser`) — "one DTO shape per concept, reused everywhere," ready for PR6's `MyRequests.razor` to reference the same shapes. **Explicitly not done in this PR**: `Approvals.razor`'s own action buttons (Approve/Deny/Decide/Activate) are still ungated by department membership — that page's deferred action-hiding gap (flagged since its own original design spec) stays open; PR5's scope was the new Capabilities page and its forms, not revisiting an existing page. DRACO verdict evidence is not surfaced on the form (ADR-012 §3 defers that to once ADR-005 Item 5's DRACO integration lands) — the optional DRACO verdict ID field is present, but nothing validates or previews it yet.

**ADR-012 PR3 addition (2026-07-17, shipped)**: Action Item 4 closes a gap that predates ADR-012 entirely — `CapabilityOverrideRequestRepository.create()`/`markApproved()`/`markDenied()` and `CapabilityOverrideExceptionRepository.createException()`/`decideReview()` were bare, untransacted `INSERT`/`UPDATE`s with **zero** `audit_log` participation. A request or a reviewer decision could exist in these tables with no corresponding hash-chain entry at all — the exact "coverage, not just integrity" gap [ADR-005](../../../docs/07-architecture/ADR-005-federated-capability-ownership.md) Action Item 6 was written against, one write-path further upstream. All five methods now open their own transaction (acquire a client, `BEGIN`, the row write, the audit_log insert, `COMMIT`; any failure `ROLLBACK`s both), so a row landing in these tables without a matching hash-chain entry is no longer reachable. `insertAuditLogDigest` (`auditLogCoverage.ts`) is the one shared call site all five route through — never a sixth hand-written `INSERT INTO audit_log`. Digest, not raw content (ADR-012 §D, hard requirement): `capability_row_digest` (migration 444, a Postgres function, not a TypeScript one — see its own comment for why: PR6's future `decide_capability_request` stored procedure needs to call the identical canonicalization from plpgsql, and Postgres's `jsonb::text` output is already canonical, so casting through `jsonb` is sufficient without a hand-rolled key-sorting step) computes `sha256(row::jsonb::text)`; `audit_log.new_values`/`old_values` store `{"digest": "..."}`, never the raw `justification` text or requester identity. **Explicitly out of scope**: `CapabilityOverrideExceptionRepository.markActivated()` (the break-glass activation step) is not covered by this PR — a deliberate, disclosed scoping choice (ADR-012 §D names `create`/`markApproved`/`markDenied` and their "exception-table equivalents" without enumerating every state-affecting method; `createException`/`decideReview` are the closest analogues to create/decide), not an oversight. A future PR should close it the same way. **Verification gap**: the transactional-integrity and rollback-on-failure proof here is a governed-feature-packet mocked-pool contract guard (REQ-CAP-011), not the real-Postgres integration test ADR-012's plan originally called for — `server/tests/integration/`'s full-app bootstrap (`tests/setup/integration-setup.js`'s `beforeEach` unconditionally `require`s `src/server.ts`) is currently broken by at least two distinct, unrelated, pre-existing issues (a `requirePermission`-shaped one and a separate `react-markdown` ESM-transform crash via `openuiChat`'s routes), discovered while building PR2 and confirmed repo-wide (not ADR-012-specific) while starting this PR. Not fixed here — flagged for separate investigation.

**ADR-012 PR7 addition (2026-07-18, shipped)**: `app/capability-registry/page.tsx` — the Researcher Dashboard's (Next.js, not the Governor Portal) first view onto `capability_registry`, calling PR4's `GET /api/v1/capability-registry` directly through the existing `/api/*` rewrite (`capability-registry` isn't in `next.config.mjs`'s excluded-prefix list, so no proxy change was needed) via a new `apiClient.getCapabilityRegistry()` typed method (`lib/api.ts`) — no bearer-token relay reimplemented, `apiClient.request` already attaches the `Authorization` header from `localStorage` the same way every other authenticated frontend call does. Deliberately read-only: no `PillButton`/dialog/form anywhere in the page, only a single outbound `<a>` link to the Governor Portal (`${NEXT_PUBLIC_ORCHESTRATOR_URL}/capabilities`, hidden entirely when that env var is unset rather than linking somewhere broken). **Correction to the plan (caught during implementation)**: the plan's task 2 originally specified deep-linking to `/capabilities/{moduleId}/{portfolioId}` — that per-capability route doesn't exist; `Capabilities.razor` is mounted only at the flat `/capabilities` list route, and adding a new orchestrator route would have contradicted this task's own "no new backend plumbing" framing. The link goes to the existing list page instead — see the plan doc's own corrected task 2 text. Contract guard is a source-scan test (`__tests__/app/capability-registry/page.test.tsx`), matching the plan's own suggested design: asserts the page source contains no `apiClient.(post|put|patch|delete)(` and no `method: "POST"/"PUT"/"PATCH"/"DELETE"` literal, plus a render test confirming no write-labeled button appears once data loads. No manifest change — this is a frontend Jest test under `__tests__/`, not the server's governed-feature packet (that packet is Node/`server/src/__tests__/` only); `npx jest` runs it directly, matching this repo's separate frontend/backend Jest configs (CLAUDE.md's "Frontend (Jest)" vs "Backend (Jest)" command split).

## Invariants

- **Must always (bugfix, 2026-07-14): `Adpa.AppHost/Program.cs`'s `apiservice` resource must carry `apiservice.WithEnvironment("CAPABILITY_REGISTRY_URL", backend.GetEndpoint("http"))` (plus `ASPNETCORE_ENVIRONMENT=Development` for local runs), or every orchestrator-side relay in this packet (`.../overrides/pending`, `.../exceptions/pending`, and all six `CapabilityController` proxy actions) 502s.** `CapabilityRegistryClient`'s `BaseAddress` resolution (`Adpa.Orchestrator/Program.cs`) only overrides its `http://adpa-backend` default to `http://localhost:5000` when `builder.Environment.IsDevelopment()` is true; without an explicit `ASPNETCORE_ENVIRONMENT`, Aspire `AddProject` resources ran as `Production` in this repo (confirmed via a real boot log), so that fallback never triggered. Real Aspire service discovery resolving the literal host `http://adpa-backend` wasn't a fallback option either: `backend` is an `AddExecutable` resource, and `WithReference`'s connection-string-based overload doesn't accept `ExecutableResource` (confirmed via a build error: `IResourceBuilder<ExecutableResource>` doesn't satisfy `IResourceWithConnectionString`) — so the fix feeds the config key directly with the backend's real resolved endpoint instead of relying on hostname resolution. Both gaps (missing explicit URL, non-Development environment) had to close together; either alone still 502s. Symptom is generic and easy to misattribute to the Node backend being down (`Could not load override requests (502)` in the Governor Portal's Approvals queue) when the real cause is upstream wiring in the AppHost, not Node itself.
- Must always: scope `capability_registry` by `portfolio_id`, not `company_id`/`tenant_id` alone — activation is per-portfolio, matching Phase 0's identity scoping.
- Must always: treat "missing a row" and "row exists but has no owner assigned" as distinct states. Reconciliation (this packet) only detects the former. Populating a real `functionalOwnerDepartment`/`controlDefinitionOwnerDepartment` value is a business decision, never guessed by a migration or the row builder.
- Must always: detect drift in both directions — a module added to the manifest with no row yet, *and* a portfolio created after the initial seed with no rows for any existing module. Checking only "new module" misses the second case.
- Must always: detect orphaned rows (a `module_id` no longer present in the manifest) as a distinct check from missing rows — a retired module's stale row must not be mistaken for a still-governed one.
- Must always: default `platformOperator` to `'IT'` and `functionalOwnerType` to `'department'` in the row builder — these are Phase 1's documented defaults, not placeholders that happen to work.
- Must always (Phase 7): resolve owner departments through `resolveModuleOwnerDepartments` (`moduleOwnerAssignments.ts`), never inline a department string at a call site — this is the one place the real business decision (which packet belongs to which department) is recorded, and every consumer (the seed runner, migration 438's backfill) must stay in sync with it, not invent a parallel mapping.
- Must never (Phase 7): treat `buildCapabilityRegistryRow`'s own null defaults as evidence that owner assignment is still unresolved — the builder itself stays a pure, business-decision-free function (defaults to null unless a caller passes an override), but `seedCapabilityRegistry.ts` always passes `resolveModuleOwnerDepartments(moduleId)` as that override now. A null owner reaching `capability_registry` today is a `NOT NULL` constraint violation (migration 439), not a valid state.
- Must always: read attestation cadence from configuration (`CAPABILITY_ATTESTATION_CADENCE_DAYS`), never hardcode the cadence as a literal at a call site.
- Must never: treat this packet's reconciliation as the actual DB-side enforcement by itself — it's the pure decision logic. The live check now exists as separate operational scripts that call it: `seedCapabilityRegistry.ts` (`npm run seed:capability-registry`, inserts missing rows via `CapabilityRegistryRepository.insertMissing`, `ON CONFLICT DO NOTHING` so it never clobbers an assigned owner) and `checkCapabilityRegistryCoverage.ts` (`npm run check:capability-registry-coverage`, a CI/deploy-pipeline gate — deliberately **not** folded into `verify:governed-features`, see the next bullet).
- Must never: extend `server/scripts/verify-governed-features.mjs` to do this reconciliation — that script is a static, filesystem-only checker with no DB access, and stays that way (CLAUDE.md documents `test:features`/`verify:governed-features` as fast and DB-free, required before every commit). `checkCapabilityRegistryCoverage.ts` is the DB-aware equivalent, kept as its own script for exactly this reason.
- Must always: keep the `GET /api/v1/capability-registry/:moduleId/:portfolioId` lookup read-only and unauthenticated-by-design (no user JWT exists on this service-to-service call) — matches the existing no-auth-header convention already used by the orchestrator's other typed HttpClients (`GovernanceApiClient`, `IntelligenceClient`); trust is via the internal network boundary, not a credential.
- Must always (Phase 6): keep `POST .../promote` authenticated and department-membership-authorized, unlike the `GET` — it's a real write path, not a service-to-service lookup. Resolve `(moduleId, portfolioId)` via `findFullByModuleAndPortfolio` (exposes `id`/`activationStatus`), not the original `findByModuleAndPortfolio` (kept unchanged since the orchestrator's `TaskApprovalGate` already depends on its exact shape).
- Must never (Phase 6): treat this endpoint's `isOverride`/`overrideExpiresAt` handling as authorization. It mechanically passes them to `promote_capability_status`, which only checks they were *recorded* — see `adpa-capability-activation-lifecycle`'s own boundary note. Phase 2 task 4's "who may grant an override" check is still unbuilt.
- Must always (ADR-012 PR2): route any new admin-sees-all/member-sees-own-active-department scoping through `buildAdminOrActiveDepartmentMemberClause`, parameterized by the two real columns — never hand-write a fourth inline copy of the `$1::boolean = true OR EXISTS (...)` shape.
- Must never (ADR-012 PR2): assume `exceptions/pending`'s authorization can be expressed through this same helper. It's a structurally different check (named-reviewer-assignment, not department membership) — forcing it through `buildAdminOrActiveDepartmentMemberClause` would silently change its actual behavior, not just its implementation.
- Must always (ADR-012 PR4): keep `listForUser`/`GET /api/v1/capability-registry` scoped by the capability's own `functional_owner_department`, never by joining `capability_override_requests` or any other request table — a capability with zero pending requests still has to appear for its owning department, exactly the divergence `buildAdminOrActiveDepartmentMemberClause` exists to prevent (see §A's corrected predicate note above).
- Must never (ADR-012 PR4): wire `Capabilities.razor`'s action buttons to a real endpoint without also gating them on the caller's resolved department membership (PR1's `CurrentUserService`). Shipping them `Disabled="true"` is fine (this PR does); shipping them enabled-but-ungated is not — that's the exact "hide an action the caller isn't authorized for" gap ADR-012 exists to close, not reopen.
- Must never (ADR-012 PR7): add a write-capable call (`apiClient.post/put/patch/delete`, or any `fetch`/`request` with a non-GET method) to `app/capability-registry/page.tsx` — the Researcher Dashboard's Capability Register view is discovery-only by design (ADR-012 §C: Experience Tier is read-only/decision, not authority); every write action routes through the Governor Portal instead. The source-scan contract guard in `__tests__/app/capability-registry/page.test.tsx` exists specifically to catch a regression here.

## Interaction Rules

- Must not break `projects` (Pillar 7) tenant/portfolio scoping — `portfolio_id` here is additive, not a replacement for `company_id`.
- Shares a manifest packet id (`federated-capability-ownership`) and test directory (`server/src/__tests__/modules/federated-capability-ownership/`) with Phase 0's `adpa-federated-capability-ownership` skill — this packet's tests must not alter Phase 0's existing test files or their asserted shapes.
- Depends on: nothing yet (additive to Phase 0, no cross-dependency per the implementation plan's sequencing note). Later phases depend on this one — Phase 2's `TaskApprovalGate` and Phase 7's `NOT NULL` constraint both read `capability_registry`'s actual row shape.
